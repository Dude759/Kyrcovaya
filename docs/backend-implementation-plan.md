# План реализации backend и завершения курсовой

Версия 1.3, 26 октября 2026 года. Stage 1 закрыт как проектные материалы; Stage 2A и Stage 2B — GREEN / CLOSED: [запуск](../backend/README.md), [публичный протокол](testing/public-results.md). Следующий узкий инкремент — Stage 3A Reservation Core, затем 3B Test Payments → 3C Confirmed Booking → 3D Charging Session. Нумерация ниже техническая; этапы 0–14 [общего плана](coursework-plan.md) относятся ко всей курсовой; технический этап 2 соответствует Stage 2A.

## Порядок и критерии завершения

| Этап | Работы | Когда можно считать готовым |
| --- | --- | --- |
| 1. Проектирование | Аналоги, персоны, карта боли, Use-case, требования, архитектура, словарь БД, контракт | Материалы связаны между собой, описаны транзакции и границы имитаторов; согласование преподавателем проверяется отдельно |
| 2. Backend и БД | TypeScript/Express, PostgreSQL, миграции, организация и seed, auth, профиль, workspace, каталог | Два браузера видят одну БД; роли проверяет сервер; данные сохраняются после рестарта |
| 3. Водитель | Удержания, тестовый платёжный провайдер, webhook, бронирование, возврат, запуск/остановка и имитатор устройств | Полный сценарий проходит через API; повтор запросов не создаёт дубликатов; конкурентная заявка проверена |
| 4. Оператор | CRUD станций/портов, сервисный режим, телеметрия и журнал | Нельзя управлять чужой организацией; оператор видит водительские сессии и подтверждённые изменения |
| 5. ГИС | Каталог и интервальная доступность из БД, фильтры и маркеры | Созданная оператором станция видна водителю после обновления API; data.ts не источник HTTP-режима |
| 6. Мощность | Grid-имитатор, max-min распределение, подтверждение команд, сценарии дефицита и потери связи | Ни один бюджет/порт не превышен; есть сравнение поведения с регулированием и без него |
| 7. ML | Набор часовой нагрузки, базовые методы, Python-модель, временная оценка, API прогноза | Есть воспроизводимый отчёт MAE/RMSE, источник набора и сравнение с baseline; UI получает прогноз модели |
| 8. Защита | Проверки, пояснительная записка, диаграммы, презентация, репетиция | Проект запускается из инструкции; демонстрация повторяется с чистыми данными и не зависит от ручной правки БД |

Этапы GIS и телеметрии частично выполняются вместе с этапами 2–4: графические экраны уже существуют. ML и распределение мощности имеют отдельные критерии; их нельзя заменить только статичным графиком.

## Первый серверный инкремент

Папка `backend/` добавляется в текущий репозиторий. Состав: конфигурация окружения, приложение Express, SQL-миграции и seed, модули auth/users/catalog/workspace, служебная команда создания оператора, интеграционные тесты на PostgreSQL. PostgreSQL запускается отдельным сервисом; применение миграций и seed — явные команды. Пароли демонстрационных аккаунтов задаются seed-конфигурацией, а не production-значениями в исходниках.

Первый набор API: health, login/register/me/logout, профиль/настройки, каталог и workspace с пустыми собственными бронями/сессиями и forecast = null. Недоступные операции пока возвращают понятный отказ и не сообщают об успехе. HTTP-фронтенд включается на локальном стенде, без преждевременного переключения публичной демонстрации.

Первая миграция ограничена `organizations`, `users`, `driver_profiles`, `user_preferences`, `auth_sessions`, `stations`, `connectors`. Seed: одна организация, оператор, несколько водителей, 6–10 станций и физические порты. В тестовых данных дополнительно создаётся вторая организация для проверки изоляции. Восстановление доступа по почте и отдельная таблица reset-токенов добавляются следующим инкрементом. Точная приёмка Stage 2A приведена в [общем плане](coursework-plan.md), проверки B01–B10 — в [тест-плане](testing/test-plan.md).

Проверки инкремента: регистрация сохраняет пользователя; дубли email отклоняются; нельзя зарегистрировать operator; токен отзывается; истёкший вход даёт 401; организация из запроса не подменяет серверную; оператор видит только свою сеть; рестарт сохраняет профиль; некорректные координаты и мощности отклоняются.

Node.js 24 используется уже в сборке frontend; для backend выбираем ту же основную версию. Схему проектируем для PostgreSQL 17. Конкретные версии Express, pg, библиотеки проверки схем и хеширования паролей фиксируются в lock-файле при реализации после проверки официальной документации. Python-модель подключается на этапе 7; её окружение и версия модели фиксируются отдельно.

## Stage 3A — ядро резервирования

Вводится только connector_reservations: один физический порт и интервал timestamptz, held/confirmed/released/expired, явная очистка истёкшего held и exclusion constraint. Создание/освобождение hold остаются внутренними SQL-транзакциями. GET availability доступен водителю и даёт оценку без удержания, из серверного профиля/тарифа. Точные ограничения — [OpenAPI](../backend/openapi/reservations.yaml); приёмка — [R-тесты и публикация](testing/reservation-results.md). До успеха CI, merge и совпадения main с Render/Pages этот этап не CLOSED.

Платёжные таблицы, webhook, подтверждённая пользовательская бронь, зарядные сессии и телеметрия не добавляются вместе с 002. Наличие состояния confirmed в constraint проверяется SQL-фикстурой в отдельной тестовой схеме, а не созданием пользовательской оплаченной брони без оплаты.

## Платежи и расчёт стоимости

В курсовой сначала используется отдельный тестовый платёжный адаптер. Он выдаёт страницу подтверждения, допускает управляемые исходы и доставляет событие backend. Успех не устанавливается обычным GET страницы возврата. В публичном стенде сессия оплаты имеет HTTPS URL; loopback-разработка настраивается отдельно и не ослабляет проверку произвольных внешних ссылок.

Сумма до зарядки — **предоплата по явно обозначенной оценке**, а не стоимость измеренной энергии. При создании сервер фиксирует метод оценки и тариф, а при завершении считает итог из фактической энергии имитатора/счётчика. Для минимальной версии задаётся энергетический бюджет предоплаты: энергия = amount/tariff. Сервер запрашивает остановку с запасом до исчерпания бюджета, учитывающим частоту телеметрии и задержку устройства. Возможные отклонения учитываются отдельно; бесконтрольное списание сверх предоплаты не реализуется.

Неиспользованный остаток возвращается тестовым провайдером. Реальная постоплата, дополнительное списание, фискализация и юридические правила возвратов — отдельные интеграции. Текущий mock использует эвристическую оценку; её нельзя описывать в записке как показание счётчика или окончательный биллинг.

## Переход от текущих DTO

- Сначала backend возвращает существующие типы для поддерживаемых состояний, сохраняя поля и строковые ID.
- Добавляем состояния истечения брони, возврата и подтверждения команд как согласованное расширение типов и соответствующих экранов. Изменение enum без обновления UI недопустимо.
- Автомобиль относится только к водителю. Для operator DTO не должен требовать фиктивного автомобиля; при реализации auth потребуется уточнить общий User/Profile и места в UI, где используются автомобильные поля.
- У источника телеметрии добавляется `simulator` для серверного имитатора. UI не выдаёт его за настоящее устройство и не пересчитывает серверный счётчик; источник local demo остаётся у mock.
- Лимиты UI становятся ограничениями из конфигурации станции/сети; допускается сеть с бюджетом ниже суммы установленной мощности. Разделяем установленную, выделенную и измеренную мощности.
- `/workspace` остаётся стартовой загрузкой; каталог, интервальные слоты и большие истории постепенно получают отдельные запросы.

## Реализованный объём Stage 3B

[Миграция 003](../backend/migrations/003_payments.sql), [OpenAPI](../backend/openapi/payments.yaml), [P00–P19](testing/payment-results.md). Неизменяемый заказ и отдельные attempts/events. POST payments атомарно создаёт pending/held/attempt с серверной ценой. User/key/request_hash защищают повторы; retry сохраняет заказ/порт/цену/TTL. Fail/cancel освобождают hold. Test provider выдаёт HTTPS страницу без карточных полей; HMAC inbox проверяет raw bytes, дедуплицирует event ID.

Успех фиксируется только у попытки: payment=pending, bookingId=null. Весь процесс с payment=succeeded, confirmed reservation и booking впервые реализуется одной транзакцией в 3C. Поздний success сохраняется для будущей сверки; реального списания или возврата в 3B нет.

## Stage 3C — реализованный инкремент

004 + finalizePayment + driver workspace + recovery тестового возврата. Проектирование 3B не изменялось задним числом: новая миграция расширяет статус и добавляет связи. Повтор старого awaiting_booking может завершить недостающую финализацию; просроченный hold получает компенсацию без брони. Подробные [границы, F-тесты и приёмка](testing/booking-finalization-results.md). 3D (start/simulator/stop/history), оборудование, ML и мощность не входят в этот выпуск.
