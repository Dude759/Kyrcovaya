# Stage 5B: применение мощности — отдельный этап

## Аудит 5A

Стартовая мощность charging_sessions.allocated_power_w входит в неизменяемый снимок:
charging_session_guard запрещает её UPDATE. measurement_guard ограничивает power_w
этим выделением и проверяет монотонность счётчика. SimulatorChargerAdapter интегрирует
энергию через elapsed × allocated_power_w и остаток watt_ms. localPowerProof проверяет
порт, локальный лимит и сумму незавершённых выделений. Порядок: advisory driver →
payment → station → connector → reservation → booking → session → command/device.
Организационный network_limit_kw был только конфигурацией, а не Grid-телеметрией.
5A не меняет эти гарантии. Планировщик читает согласованный снимок, сохраняет только
grid_* и power_plan_*. Его org advisory lock не захватывает блокировки платежей.

## Требуемые решения до реализации

1. Не снимать защиту снимков сессии. В новой миграции добавить отдельное текущее
   подтверждённое состояние мощности и неизменяемую историю переходов с effective_at.
   allocated_power_w остаётся стартовым снимком; requested/planned/acknowledged/measured
   имеют разные источники. Requested на 5A — стартовое локальное выделение (proxy
   спроса), поскольку отдельный пользовательский запрос мощности раньше не хранился.
2. Добавить setPower с durable intent, стабильным provider_command_id и идемпотентным
   receipt. pending/submitted не означают применение. API изменения устройств пока нет.
3. Перед сменой мощности имитатор должен закрыть энергетический интервал старой
   подтверждённой мощностью до effective_at. Новый интервал использует новую мощность;
   не пересчитывать прошлое и не применять новую мощность ко всему elapsed. Остаток
   watt_ms сохранять, предоплату и energy_budget_wh проверять до и после команды.
4. measurement_guard сверяет показание с подтверждённым пределом на sampled_at,
   а не с последним расчётным планом. Финальный расчёт продолжает использовать только
   подтверждённый накопительный Wh и зафиксированный тариф.
5. Применять только пригодный план с проверкой revision всех входов; зафиксировать
   единый порядок блокировок с текущими start/stop, отменой и операторским архивом.
   План мог устареть из-за новой сессии или локального лимита: тогда пересчитать.
6. Заранее выбрать политику offline/stale: безопасное снижение/пауза требует отдельной
   подтверждаемой команды. Без receipt нельзя объявить мощность сниженной или ресурс
   свободным. При неопределённом применении порт остаётся зарезервированным.
7. После сна Render: не достраивать энергию за отсутствующие показания. Сначала
   сверить долговечные receipts/устройство, отметить gap, затем перепланировать;
   повтор command_id не даёт повторного эффекта. ML не имеет права обходить Grid/порт.

## Приёмка 5B

Отдельная PG17: delayed/duplicate/rejected receipts, concurrency start/stop/setPower,
смена мощности внутри часа, предоплата/резерв/тариф, sleep/restart/rollback, stale/offline,
восстановление и повтор сверки. До этих проверок 5A остаётся исключительно shadow.

## Решения реализации 5B (до изменения кода)

- Режим применения — настройка организации, по умолчанию OFF. Переключение только
  без незавершённых сессий и команд. Старые зарядки не мигрируют. Включение требует
  live-сценарий и свежий положительный Grid; training никогда не применяется.
- Порядок: advisory dispatch:organization → advisory driver → payment → station →
  connector → reservation → booking → session → command → simulator state.
  Изменения оператора и Grid scenario берут dispatch до своих блокировок. Расчёт
  читает все входы под org lock, но не блокирует несколько графов платежей сразу.
  Исполнение каждой команды заново рассчитывает входы под тем же org lock.
- Immutable dispatch plan содержит fingerprint Grid, лимитов, доступности, demand
  и состава сессий. Shadow-таблицы не меняются. Устаревшая команда отклоняется как
  superseded, следующий проход создаёт актуальную. Снижения идут до повышений.
  Повышение разрешено лишь если сумма подтверждений и ещё не подтверждённых стартов
  укладывается в свежий бюджет. Неизвестный Grid требует 0 Вт и запрещает старты.
- Адаптер атомарно закрывает старый энергетический интервал, пишет durable receipt,
  history/effective_at и confirmed state. Получение receipt восстанавливает статус
  команды после потери ответа. Последовательность защищает от старых команд.
- 0 Вт — подтверждённая пауза до конца оплаченного окна. Offline устройства оставляет
  команду неподтверждённой и порт занятым. После смены epoch или паузы >15 с энергия
  за разрыв не начисляется. Тариф, settlement и предоплата остаются неизменными.
- БД проверяет связь receipt/history/state и мощность по истории на sampled_at.
  Fault/race/restart тесты — отдельная PG17. Production: OFF → регрессия → две учебные
  сессии → дефицит/восстановление/stop/refund → возврат OFF и безопасного Grid.
