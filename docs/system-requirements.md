# Требования к платформе «Энерготранспорт»

Версия 1.2, 26 октября 2026 года. Рабочее ТЗ; описание учебной программы получено со слов пользователя, оригинал и требования преподавателя ещё нужно проверить. Документ описывает целевую систему. Состояние Foundation обновлено по [протоколу](testing/backend-results.md); идентификаторы F01–F16 сохранены.

## Тема и цель

Тема: разработка платформы «Энерготранспорт» для мониторинга и управления зарядной инфраструктурой электромобилей.

Цель: объединить поиск станций, резервирование разъёмов, учёт зарядных сессий, прогноз нагрузки и распределение ограниченной мощности в одной информационной системе. На защите система должна воспроизводимо показывать полный сценарий водителя и реакцию сети на дефицит мощности.

## Текущее состояние

| Часть | Подтверждённое состояние |
| --- | --- |
| Frontend | Опубликованная версия — mock; локально подключается к Express командой dev:server |
| ГИС | В HTTP-режиме настоящая Яндекс Карта получает координаты PostgreSQL через API; проверено на localhost |
| Авторизация | Серверные register/login/me/logout, scrypt, отзываемые токены; профиль/настройки в БД |
| Бронирование, платежи, зарядка | Рабочие демонстрационные сценарии в браузере; банковских списаний и оборудования нет |
| Оператор | Экраны мониторинга, мощности, сессий и настроек; добавление станций и физических портов требует API и небольших расширений интерфейса |
| Backend, PostgreSQL | Foundation реализован и проверен локально: семь предметных таблиц, миграции, seed |
| ML и мощность | Спроектированы; серверная реализация ещё отсутствует |

Прогресс определяется выполнением критериев ниже, без приблизительного процента готовности всего проекта.

## Роли

**Водитель** регистрируется самостоятельно, работает только со своим профилем, платежами, бронями и сессиями. Может просматривать доступные станции других организаций.

**Оператор** получает аккаунт от администратора; публичная регистрация оператора отсутствует. Работает со станциями и сессиями своей организации. Факт выбора роли на странице входа не даёт дополнительных прав.

**Администратор** в минимальной версии использует служебную команду для создания организации и выдачи операторских аккаунтов. Отдельный административный кабинет не входит в обязательный объём.

## Функциональные требования и приёмка

| ID | Требование | Проверяемый результат |
| --- | --- | --- |
| F01 | Серверная регистрация и вход | Пользователь хранится в БД, пароль хранится как стойкий хеш; после входа выдаётся отзываемый токен |
| F02 | Разделение доступа | Другой водитель не может получить чужой платёж или начать чужую зарядку; оператор другой организации получает отказ |
| F03 | Каталог и ГИС | API возвращает станции БД, карта строит маркеры из ответа; работают поиск, фильтры и карточка |
| F04 | Физические порты | Каждый порт имеет собственный ID, тип, мощность и состояние; группировка в интерфейсе не заменяет учёт портов |
| F05 | Интервальное бронирование | Две конкурентные заявки на последний порт одного интервала не создают две подтверждённые брони; соседние интервалы допустимы |
| F06 | Платёжный процесс | Тестовый платёж создаётся сервером; подтверждение приходит от адаптера, а повтор события не создаёт новую бронь |
| F07 | Отмена и истечение | Неоплаченная попытка и временное удержание истекают; отмена оплаченной брони инициирует тестовый возврат |
| F08 | Полный цикл зарядки | Подтверждённая бронь запускает одну сессию; завершение фиксирует энергию, время и итоговый расчёт в БД |
| F09 | Телеметрия | Данные имитатора поступают серверу; при потере связи последнее показание сохраняется, текущая мощность помечается неизвестной |
| F10 | Управление объектами | Оператор создаёт/редактирует станцию и порт, задаёт лимит, переводит объект в сервисный режим; действия журналируются |
| F11 | Безопасное обслуживание | Сервисный режим не включается во время активной зарядки; удаление исторически используемого объекта заменяется архивированием |
| F12 | Прогноз | API отдаёт 24 часовых значения, время расчёта и источник; качество проверяется на отложенном временном периоде |
| F13 | Распределение мощности | Выделенная мощность неотрицательна, не превышает запрос автомобиля/порт/станцию/сеть; дефицит воспроизводится в сценарии |
| F14 | Энергосистема | Сервер получает доступную мощность и состояние от явного имитатора; потеря связи не выдаётся за нормальное состояние |
| F15 | История и экспорт | Завершённые сессии доступны после перезапуска сервера; CSV содержит согласованные с БД значения и не называется кассовым чеком |
| F16 | Настройки и восстановление | Настройки сохраняются в БД; ссылка восстановления одноразовая и ограничена по времени, входы отзываются после смены пароля |

## Границы обязательной учебной версии

Обязательно: основной backend на Node.js/TypeScript/Express, PostgreSQL, существующий React frontend, Яндекс Карты, платёжный адаптер с тестовыми исходами, имитатор зарядных устройств и энергосистемы, одна обученная модель, алгоритм распределения мощности, интеграционные проверки и пояснительная записка.

Вне обязательного объёма: банковские списания, фискализация, договор с энергокомпанией, управление настоящими зарядными контроллерами, полный OCPP-шлюз, мобильное приложение, микросервисная инфраструктура. Интерфейсы адаптеров позволяют добавить эти интеграции позднее. Подключение банковской песочницы — отдельное расширение, а не условие первого рабочего backend.

Для почтового восстановления при разработке допустим локальный почтовый приёмник. На публичном стенде без почтового сервиса функция показывает честное сообщение о недоступности; токены восстановления не выводятся в общедоступные логи или API.

## Нефункциональные требования

- PostgreSQL — источник истины для серверного режима. Перезапуск backend не сбрасывает пользователей, бронь или историю.
- Проверка входных данных, роли и принадлежности выполняется на сервере. ID и цена из клиента не считаются доверенными.
- Время хранится как `timestamptz`, API использует ISO 8601 с часовым поясом; представление — Europe/Moscow. Мощность — кВт, энергия — кВт⋅ч. Деньги в БД — целые копейки, в совместимых DTO — рубли.
- Финансовые и резервирующие операции атомарны и повторяемы без дубликатов. Внешние HTTP-запросы не удерживают транзакцию БД открытой.
- Секреты находятся в серверном окружении. Публичный браузерный ключ карты ограничен разрешёнными доменами. CORS разрешает конкретный frontend origin.
- Публичный backend использует HTTPS. Токены и персональные данные не попадают в журналы ошибок; пользовательские ответы не содержат стек сервера.
- Телеметрия обновляется в имитаторе каждые 10 секунд; состояние старше 60 секунд считается устаревшим. ML-расчёт обновляется раз в час.
- Целевой учебный стенд: 6–20 станций, до 200 физических портов, 50 одновременных пользователей. Обычные чтения API: p95 ≤ 1 с при измеренном прогоне этого сценария, без включения внешних карт/платежей. Это цель проверки, а не уже измеренный результат.
- Основные экраны работают от 320 px и доступны с клавиатуры; новые формы сохраняют действующий стиль.

## Критерий готовности проекта

В чистой БД применяются миграции и демонстрационные данные. Два независимых браузера используют один API. Водитель проходит бронь → тестовую оплату → зарядку → завершение; оператор видит эту сессию, изменяет лимит и наблюдает изменение мощности. История сохраняется после рестарта. При конкурентном бронировании не возникает двойной резерв. Прогноз имеет отчёт сравнения с базовым методом; ограничения мощности проверяются автоматически. Все имитационные источники подписаны.
