# План курсового проекта v1.3

26 октября 2026 года. Рабочий план проекта «Энерготранспорт», основанный на фактическом состоянии репозитория и описании учебной программы, приведённом пользователем. Это не утверждённый колледжем документ: оригинал программы, требования к оформлению, сроки и согласование преподавателя ещё нужно получить и проверить. Число учебных часов и обязательность конкретного ГОСТ здесь не устанавливаются по пересказу.

## Постановка задачи

**Тема:** разработка платформы «Энерготранспорт» для мониторинга и управления зарядной инфраструктурой электромобилей. Название соответствует исходному заданию; «Электротранспорт» в пересказах плана не является переименованием проекта.

**Объект:** инфраструктура зарядных станций для электромобилей. **Предмет:** программные методы мониторинга, бронирования и управления мощностью зарядной инфраструктуры. **Цель:** разработать веб-платформу, объединяющую поиск станций, резервирование физических портов, учёт зарядных сессий, прогноз нагрузки и распределение ограниченной мощности.

Задачи:

1. Проанализировать предметную область и официальные описания аналогов.
2. Определить роли, пользовательские проблемы, варианты использования и проверяемые требования.
3. Спроектировать архитектуру, БД и контракт API.
4. Реализовать интерфейсы водителя и оператора, интегрировать ГИС.
5. Разработать сервер, постоянное хранение данных и авторизацию.
6. Реализовать конкурентное бронирование, тестовую оплату и серверный цикл зарядки.
7. Реализовать мониторинг и распределение мощности с имитатором энергосистемы.
8. Создать и оценить модель 24-часового прогноза на отдельном временном периоде.
9. Провести тестирование, подготовить документацию, демонстрацию и защиту.

Границы учебной реализации заданы в [требованиях](system-requirements.md): платежи и оборудование имитируются явно. Реальные банковские списания и промышленная интеграция не являются условиями завершения курсовой.

## Контрольная точка Stage 2A — GREEN / CLOSED локально

Реализована 26.10.2026: [инструкция](../backend/README.md), [локальная приёмка](testing/backend-results.md). Дополнительно выполнен Stage 2B: серверная демонстрация опубликована и проверена через HTTPS; [публичный протокол](testing/public-results.md). Следующая контрольная точка — Stage 3A: конкурентное резервирование. Ниже сохранён объём Foundation для воспроизведения приёмки.

Реализация подробно расписана в [плане backend](backend-implementation-plan.md). Здесь фиксируется минимальный объём, чтобы не реализовывать всю будущую схему заранее.

**Состав:** `backend/`, TypeScript + Express, конфигурация окружения, подключение `pg`, обработка ошибок, `/health`, SQL-миграции и seed. Первая миграция содержит только `organizations`, `users`, `driver_profiles`, `user_preferences`, `auth_sessions`, `stations`, `connectors`. Seed создаёт одну организацию, оператора, несколько водителей и 6–10 станций с физическими портами. Пароли задаются конфигурацией seed.

**Модули:** auth, users, catalog, workspace. Публичная регистрация создаёт только driver, оператор выдаётся служебной командой. Bearer-токен случайный, в БД только его хеш; выход отзывает сессию. Профиль и настройки сохраняются в БД. Каталог читается из БД; `/workspace` отдаёт пустые собственные брони/сессии и `forecast = null`. Пути и DTO берём из существующего контракта `/api`, не вводим второй несовместимый набор адресов.

В HTTP-режиме основные экраны не используют локальных пользователей и локальный каталог. Mock остаётся отдельным режимом демонстрации. Недоступные в Stage 2A бронь, платежи, зарядка и прогноз не выдают локальный успех за серверный; UI сообщает о недоступности. Восстановление по почте и `password_reset_tokens` добавляются отдельным последующим инкрементом.

**Приёмка — только после фактического прогона:**

- Чистая PostgreSQL разворачивается командами миграции и seed; повтор seed не создаёт неконтролируемых дублей.
- Регистрация, login/me/logout работают; дубли email, operator-регистрация, неверные данные, истёкший и отозванный токены проверены.
- Изменённые профиль и настройки сохраняются после перезапуска процесса; старый действующий токен продолжает работать до срока/отзыва.
- Два независимых браузерных контекста видят общий каталог. Контролируемое изменение станции в БД видно в ответе API и маркере после обновления.
- Операторские данные ограничены организацией; ID организации от клиента не даёт дополнительных прав. Публичный каталог доступен водителю согласно ТЗ.
- `/workspace` не содержит чужих объектов или выдуманных броней, сессий и прогноза.
- Проверки валидации, доступа и сохранности проходят на настоящей PostgreSQL; результаты записаны с командой, датой и commit.

Бронирования, платежи, телеметрия, интеграционные задания и ML не входят в первую миграцию. До достижения этой точки публичный frontend остаётся демонстрацией, а переключение на API выполняется на локальном стенде.

## Управление изменениями

Начиная со Stage 2B обязательна публикация стабильного этапа: [GitHub → PR/CI → main → deploy → public smoke](public-demo.md). Stage 2A + 2B дают доступную преподавателю серверную демонстрацию, подтверждённую [публичным протоколом](testing/public-results.md). Далее Stage 3A Reservations → 3B Test Payments → 3C Charging Session, с публикацией каждого инкремента.

Изменение этапа отражается здесь, в ТЗ, API и тест-плане. Для каждой принятой версии фиксируются артефакты в Git; для выполненных проверок — commit, окружение, команда и результат. Точные версии серверных зависимостей выбираются при реализации по официальной документации и фиксируются lock-файлом. Новые требования преподавателя сначала сопоставляются с текущими материалами, затем корректируется объём работ.
